# Architecture Implementability Review — Solu-2

Scope: `planning/ARCHITECTURE.md`, Module 3 only. Review owners are Mariana (Architecture Lead) and Julian (Peer Reviewer). Findings are real implementation blockers or ambiguity risks; no production logic is proposed.

| ID | Severity | Affected artifact / AD-n | Defect | Implementation risk | Recommendation | Triage | Rationale | Owner | Phase resolved |
|---|---|---|---|---|---|---|---|---|---|
| IMP-01 | High | Architecture §§7–10; AD-1, AD-6, AD-7 | IDs are named but formats and maximum lengths are undefined. | Adapters may disagree on UUID/string handling; uniqueness and FK behavior drift. | Define event/command IDs as UUID, node IDs as `^[a-z0-9][a-z0-9-]{0,62}$`, device/boot/workload IDs as non-empty strings with explicit maxima. | ACCEPT | Needed for DTO, OpenAPI, and SQL agreement; it does not add domain behavior. | Mariana | Phase 1–2 |
| IMP-02 | High | Architecture §§7.2, 9; AD-3, AD-6, AD-8 | Optional heartbeat fields and state-loss nullability are not fully enumerated. | Producers can serialize incompatible `null`/omitted values and accidentally clear current facts. | Define exact required/nullable DTO fields; only `previousBootSessionId` and external context may be null under documented guards. | ACCEPT | Nullability is an interface property required before red tests. | Mariana | Phase 1 |
| IMP-03 | High | Architecture §§6.1, 9; AD-1 | Error names lack a complete HTTP mapping and response body. | API adapters may return inconsistent 200/409/422 semantics and clients cannot distinguish retries. | Add one typed error catalog and common `ErrorBody`; make duplicate identical events successful idempotent responses, not errors. | ACCEPT | Converts existing behaviors into an implementable ingress contract. | Julian | Phase 1–2 |
| IMP-04 | Critical | Architecture §§6.1, 10; AD-1 | Compare-and-swap is required but conflict result/retry ownership is undefined. | Lost updates or unbounded internal retries can violate single-writer determinism. | Require atomic conditional mutation; return `ERR_REVISION_CONFLICT` (409, retryable) if the expected revision is stale; no SELECT-then-UPDATE. | ACCEPT | Physically enforces AD-1 without inventing policy. | Mariana | Phase 1–2 |
| IMP-05 | High | Architecture §§6.1, 7.2; AD-1, AD-6 | Equal timestamps, duplicate IDs, and changed payload reuse are described, but fingerprint canonicalization is unspecified. | Semantically identical JSON may hash differently or changed payloads may be accepted as duplicates. | Canonicalize validated DTO content and persist a SHA-256 payload hash with unique `event_id`; mismatch is `ERR_IDEMPOTENCY_CONFLICT`. | ACCEPT | Required to make replay semantics testable across adapters. | Julian | Phase 2 |
| IMP-06 | Critical | Architecture §6.6; AD-5 | Flapping has no classifier while the edge case is mandatory. | A builder may invent a debounce threshold or expose raw five-second oscillation. | Preserve the accepted evidence-only baseline: raw observations cannot mutate public state/cordon/alerts; upsert one policy-unresolved diagnostic until ODD-5 is approved. | ACCEPT | This is already a Plan-2 decision and is deterministic without hidden hysteresis. | Mariana | Phase 1–2 |
| IMP-07 | High | Architecture §§10–11; AD-3–AD-7 | Explainability is prose-rich but lacks a reusable typed payload. | UI and events can drift in rule/evidence fields; state changes may be unexplainable by API clients. | Define `ExplanationDTO` with rule IDs, observed values, thresholds/expected state, evidence IDs, policy version, prior/result state. | ACCEPT | Implements the existing causal-explanation requirement. | Mariana | Phase 1–2 |
| IMP-08 | Critical | Architecture §6.5; AD-7 | Concurrent repeated maintenance requests lack an explicit uniqueness key and identical/conflicting behavior. | Duplicate locks/events or reason/window overwrite can occur. | Use `requestId` idempotency plus one partial unique active lock per node; identical replay returns prior result, changed reuse conflicts. | ACCEPT | Makes maintenance races physically enforceable. | Julian | Phase 1–2 |
| IMP-09 | Medium | Architecture §11 Backpressure; NFR-12 | Queue/buffer bounds are explicitly unselected and overload behavior is not claimable. | A future implementation may imply unlimited buffering or silently drop accepted inputs. | Defer numeric capacity; contractually forbid silent drops and production-capacity claims, expose `ERR_INGRESS_UNAVAILABLE` only at an adapter that has not accepted the event. | DEFER | No authoritative bound exists; selecting one would invent a performance policy. | Mariana | Phase 3/implementation setup |
| IMP-10 | Medium | PRD ODD-2; Architecture §6.1 | Dedup retention and out-of-order acceptance window remain open. | Durable cleanup or ancient replay behavior cannot be finalized. | Keep ODD-2 deferred; Solu-2 schema enforces uniqueness for retained rows and makes no retention claim. | DEFER | Authoritative artifacts explicitly forbid choosing the numeric window. | Julian | Later human decision |

Triage totals: **ACCEPT 8 / DEFER 2 / REJECT 0**.

The accepted findings are applied in `planning/detailed-design/` and the Solu-2 stack section. Deferred items are explicit non-claims and do not weaken thermal, silence, reboot, maintenance, idempotency, or flapping containment.
